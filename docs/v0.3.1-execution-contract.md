# PerfLens v0.3.1 implementation and acceptance contract

[简体中文](v0.3.1-execution-contract.zh-CN.md)

This is not the product capability roadmap. Docker functionality, security, and acceptance
requirements are defined by
[`docker-container-roadmap.md`](docker-container-roadmap.md). This document defines how to
implement that roadmap continuously and recover reliably after conversation compaction,
attachment conversion, ordinary execution, or reopening the project.

## 1. Why the implementation contract is separate

A long-running task should not copy the whole roadmap, old chat history, and every test log into
its prompt. Repetition increases conflicts, while stale status can override newer Git evidence.

v0.3.1 uses this fixed source precedence:

1. the current Git worktree, commit history, and test results;
2. repository-root `AGENTS.md`;
3. the bilingual Docker roadmap;
4. this execution contract.

Chat history, old attachments, UI file counts, and earlier verbal stage reports are not progress
truth. Ignore them when they conflict with Git.

## 2. Recovery protocol at start and every continuation

Before changing files at the start of a run or continuation, execute:

```bash
git status --short
git log --oneline --decorate origin/main..HEAD
git diff --stat
git diff --check
```

Then recover using these rules:

- the `v0.3.0` tag and `origin/main` are the released baseline and are never moved or replaced;
- tested commits in `origin/main..HEAD` are completed work and are not reimplemented;
- uncommitted files belong to the current stage and are reviewed and validated before any discard,
  commit, or rewrite;
- determine the stage from the changed contracts, schemas, implementation, and tests, not from a
  conversational `Stage N` label;
- when code, roadmap, and stale status disagree, use code, tests, and the roadmap and explain the
  conflict before continuing;
- report a blocker only when the same blocking condition genuinely persists; a test failure alone
  is not a reason to end the task.

No attachment path may be the sole copy of a requirement. Even if the task text becomes a
`pasted-text` attachment, the repository and Git must be sufficient to recover.

## 3. Fixed implementation loop

Each iteration handles one logically complete, reversible subfeature:

1. identify the first incomplete roadmap capability;
2. review existing uncommitted work and preserve what can be proven correct;
3. complete success, security-denial, resource-bound, identity-replacement, and tampering tests;
4. run the relevant Ruff, Pyright, pytest, Rust, protocol, and schema checks;
5. review public artifacts, errors, logs, and Agent-visible projections for sensitive disclosure;
6. create one independent commit only after every stage check passes;
7. report the commit, tests, remaining boundary, and next stage;
8. continue automatically without waiting for another “continue” message.

After each commit, use this compact checkpoint:

```text
Checkpoint
- HEAD: <commit>
- Completed: <roadmap capability>
- Validation: <commands and results>
- Worktree: clean | <current uncommitted stage>
- Next: <one next stage>
- User action required: none | <reason>
```

The checkpoint is a summary, not a copy of long logs. Detailed proof belongs in tests, artifacts,
and Git commits.

## 4. Fixed v0.3.1 implementation order

The order follows section 10 of the Docker roadmap:

1. Docker public artifacts, schemas, and capability discovery;
2. fixed Docker adapter, socket identity pinning, and bounded sanitized parsing;
3. container ID, host PID, UID, start time, namespace, cgroup, and PID-reuse validation;
4. cgroup v2 snapshots, deltas, quality model, and verifier;
5. existing-container single-PID plan → policy → broker → artifact flow;
6. Container Gate, temporary test-container launch, and failure cleanup;
7. `per_run`, conversation-scoped `bounded_session`, revocation, expiry, and budgets;
8. rootless, same-UID, and explicitly authorized rootful boundaries with independent Broker/Helper
   validation;
9. container modules, Build IDs, source mapping, software-PMU fallback, and diagnosis binding;
10. CLI, `perflens init --docker`, MCP, Skill, Codex/Claude configuration, and matched A/B;
11. both DEBs, upgrade/rollback/removal, host regression, bilingual documentation, and the real
    Docker matrix.

A large milestone may use several small commits, but Docker execution cannot be exposed before
identity, authorization, and denial paths exist.

## 5. Autonomy and pause boundaries

The implementer may read files, edit in-scope repository code, run non-destructive checks, build
local packages, and create local commits. The following are not authorized by this contract:

- `sudo`, sysctl, systemd, `/etc`, or deployed Collector changes;
- push, tag creation/movement, or Release publication;
- reset, amend, commit deletion, or changing an existing stash;
- Docker installation, Docker-group changes, or rootful-policy activation;
- v0.4.0 Runtime Lock Adapter implementation;
- lowering coverage, deleting tests, weakening security checks, or raising global timeouts to hide
  failures.

When root, real Docker, or host-service acceptance is required, first finish everything possible as
an ordinary user, combine the commands into one reviewable batch, then pause for the user. Continue
from the Git checkpoint after receiving the complete output. Continuous execution removes repeated
“continue” messages; it does not bypass required administrator authorization.

Stop immediately when the user says “pause”, “stop”, or “do not edit yet”.

## 6. Completion conditions

The v0.3.1 implementation ends only when all of these are true:

- every stable Docker feature in the roadmap is implemented;
- each subfeature has an independent commit and passing success, denial, and boundary tests;
- Ruff, Pyright, the full Python suite, Rust, protocol, and schema checks pass;
- coverage is at least 85%;
- container paths for `stat`, `record`, `sched`, `off_cpu`, and `lock` respect feature profiles;
- software-PMU fallback, symbol/source binding, and matched A/B do not overclaim evidence;
- both v0.3.1 DEBs pass build, install, upgrade, rollback, removal, and Docker non-activation smoke;
- the v0.3.0 Linux-host path has no regression;
- English and Chinese documentation match the implementation;
- the required real-Docker/host matrix has been run and passed by the user;
- the worktree is clean;
- the final report lists commits, validation evidence, known boundaries, and local installation and
  acceptance commands.

Without real-host evidence, the task pauses for input and cannot claim completion.

## 7. Execution modes and context recovery

This contract does not depend on Codex Goal mode. Ordinary execution and persistent-task modes
must follow the same Git checkpoints, single-stage tests, and completion conditions. To resume,
read `AGENTS.md`, both Docker roadmaps, and this document in full, then continue from the first
Git-proven incomplete stage.

Do not treat stale chat, attachment stage labels, or UI file counts as current progress, and do not
repeat committed work after changing execution modes. After context compaction, recheck Git first;
keep detailed evidence in tests and commits and report only compact checkpoints in chat.
