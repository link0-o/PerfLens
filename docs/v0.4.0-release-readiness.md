# PerfLens v0.4.0 release-candidate readiness

[简体中文](v0.4.0-release-readiness.zh-CN.md) | English

Status on 2026-09-18: **the final local release gates, real-host installation/Collector acceptance,
the locally available host Runtime Lock paths, and the single-confirmation Docker integration
passed; the fixed-version matrix and controlled-host Native overhead gate are still pending**.
This record describes the untagged `0.4.0` candidate after the eight staged
Runtime Lock commits. It does not claim that a GitHub Release exists, does not replace remote CI,
and does not move the immutable `v0.3.2` tag.

## Candidate scope

The candidate adds strict Runtime Lock Evidence schema 1.1, bounded sessions, independent replay
verification, Native pthread, Java JFR, CPython threading, and Go pprof Adapters. It also lets an
explicit Docker optimization Preview include Runtime Lock authority in the same user confirmation.
It does not add live JVM/native/Python injection, arbitrary existing-container injection, a new
privileged Helper capability, or automatic commit/push/tag/release behavior.

## Real-host installation and Collector evidence

An administrator completed the `0.3.2-1` to `0.4.0-1` upgrade on a Debian 13 amd64 host. Both
packages report `0.4.0-1`, and the CLI, MCP server, and administrator CLI report `0.4.0`. Package
installation did not change the activation state of the three enabled services. After the explicit
administrator upgrade, the unprivileged Collector, bounded stat/record Helper, and independent
Trace Helper all passed their health checks. The deployed policy content and retained state were
preserved.

All fixed Runtime Lock payloads are `root:root` and have no file capabilities. The pthread probe is
mode `0644`; the Runtime Lock supervisor and container Gate are mode `0755`. The Native probe also
passed `GNU_RELRO` and `BIND_NOW` checks. The deployed Collector policy is root-owned mode `0644`;
the invoking-user-owned, not-yet-deployed policy candidate remains mode `0600`. These are distinct
trust states and must not be conflated.

The real one-second Host Collector acceptance `acceptance-f272e6a1a5605bd819fc` reports `passed`:
software counting, `cpu-clock` sampling, and target-filtered `sched`, `off_cpu`, and `lock` Trace
all succeeded. Each Trace Evidence artifact is `complete`; deterministic analysis/verification is
`partial` and preserves its evidence limitations. The host hardware PMU was unavailable, so this
acceptance cannot support IPC, cache-miss, or branch-miss conclusions.

The host exposes JDK 25.0.4.1, CPython 3.12.13/3.13.5, and Go 1.24.4. The generic Host Collector
acceptance project did not bind safe Adapter targets and tool paths, so active Adapters appearing
as `unavailable` in `status` is the expected project configuration state, not a missing
implementation. Real Adapter Evidence collection remains subject to the separate content-bound
session acceptance below.

The first real Adapter sessions completed the Native pthread exact and JDK 25 JFR thresholded main
paths. Native Run `runtime-lock-run-279a6571fc25b673a2e8` and the Java Run exited normally as the
ordinary user, and both sessions were then explicitly revoked. The stronger capture-time
verification records persisted for both runs are `verified` and contain path-free, content-bound
source replay receipts. A later public-Evidence-only verification conservatively reports `partial`
when the private source stream is absent; it must not overwrite or downgrade the stronger
capture-time record.

The Native Evidence reached the 20,000 exact-event ceiling and is therefore `partial`. It proves
that event ceilings, pairing, wait/hold aggregation, and truncation disclosure work, but it is not
an untruncated exact release result and must be rerun at a lower event rate. JDK 25 balanced JFR
recorded monitor waits over the 10 ms threshold with call stacks. An unrecorded event still cannot
be interpreted as no wait, and JFR lacks complete acquire/release pairing, so exact contention
counts, owner relationships, and hold-time conclusions remain forbidden.

That run and the subsequent Python-matrix replay exposed four release defects now fixed in the
candidate source. The common Debian
`/usr/bin/python3` symlink is now only a discovery hint; authorization still binds the resolved,
non-symlink interpreter. Descriptor execution now also binds a non-group/other-writable Runtime Home directory
and supplies its fixed descriptor path internally, so relocatable CPython 3.12 can find its
standard library without accepting arbitrary environment. In addition, `perflens status` now
performs the same safe, read-only Adapter discovery as MCP, isolates one unsafe Adapter from the
other status rows, and does not misreport an absent discovery context as “not implemented.” The
corrected DEBs were rebuilt twice with identical bytes and passed isolated package smoke.

On 2026-09-12 a freshly reloaded Claude Code project created five independent content-bound
Previews and used one human confirmation to authorize them before collecting them sequentially.
Native pthread exact produced 3,908 untruncated events, JDK 21 JFR produced 21 thresholded events,
CPython 3.13.5 produced 2,616 exact events, and the Go 1.24.4 private file backend produced separate
non-empty mutex and block cumulative profiles. All five Runs passed deterministic verification;
their persisted capture-time Verification artifacts contained non-null source replay receipts and
all ten checks passed. Evidence loss and truncation counters were zero. Evidence `quality.status`
and Run `quality_status` remain separate layers: for example, the Native Evidence was `complete`
while the Native Run remained conservatively `partial`.

The first Agent report incorrectly inferred that the five Run Finalizations were absent from the
later explicitly revoked Session revisions. Direct Artifact inspection confirmed five immutable
`outcome=completed` Finalizations bound to the corresponding Runs and revision-2 settled Sessions:
`runtime-lock-run-finalization-f78296fe73a5e913a43b`,
`runtime-lock-run-finalization-90972afbd1a221f5d255`,
`runtime-lock-run-finalization-507a0445fe32c91ae2b5`,
`runtime-lock-run-finalization-fadc897f74a6e83a64ec`, and
`runtime-lock-run-finalization-b08154f2e7c66ecc395c`. The candidate now returns the Finalization
ID/digest and settled Session revision directly in every successful collection reference, and the
Skill explains that a subsequent revision-3 revoke intentionally has no new settlement marker.
On 2026-09-13 a freshly installed-package Agent repeated all five paths with one human confirmation.
Every collection returned all four discovery fields, every referenced Finalization was
`outcome=completed` and matched its Run and revision-2 settled Session, and every Finalization
remained byte-identical after the explicit revision-3 revoke. This discoverability regression
therefore passed. The run also exposed a presentation-only inconsistency: CPython and both Go
backends omitted `target_uid` and `evidence_bytes` from their returned summaries even though the
persisted Run/Evidence retained the data. The candidate now emits both fields consistently and has
regression assertions; the freshly built package still needs the corresponding Agent retest.

On 2026-09-15 the next package run completed Native and JDK 21 host collection, then stopped at
CPython because the acceptance Preview omitted the workload's `"2"` argument while authorizing a
three-second exact window; the unchanged workload defaults to five seconds. Six earlier artifact
chains with that argument completed in the same three-second collection budget, so the acceptance
input has been restored without widening the Runtime Lock limit. The same run also exposed that a
Docker Preview could display but not request an exact Native binding, and that zero JFR DataLoss
bytes were not directly readable. The candidate now accepts an explicit Adapter-to-semantics map
and publishes `quality.lost_source_bytes`; both changes have focused regression coverage and still
require a freshly installed-package Agent retest.

A subsequent freshly installed-package run exercised all five host Adapters successfully: every
workload passed correctness, every capture-time Verification passed all ten checks with a source
replay receipt, and the Native/JFR Evidence loss and truncation counters remained zero. Its Docker
baseline build also succeeded, and the Broker persisted a complete 1.041-second software `stat`
Collection without fallback. The enclosing call then failed before Container Run, Benchmark,
Measurement, and Runtime Lock finalization because the three-second workload timeout had started
before container preparation and integer rounding left the two-second workload only about one
second for Docker wait. The candidate now uses a precise Gate-release-relative deadline and
reports a genuine wait expiry at the Docker-workload stage. A rebuilt-package Docker retest remains
required.

That rebuilt-package retest confirmed the Gate-relative timeout fix: the Broker persisted a
complete 1.027-second software `stat` Collection for the same two-second workload, and Docker wait
no longer expired. All five host Adapter paths also completed again with verified source replay
and untruncated Evidence. Finalization then exposed a second independent defect: Benchmark capture
required the scratch leaf to be `0700`, while the managed coordinator, Docker mount validator, and
Runtime Lock capture correctly require that container-writable leaf to be `0733` beneath a private
`0700` run directory. The candidate now validates that actual two-level layout and independently
binds the Benchmark file owner to the verified target host UID. The Container Run/Benchmark/
Measurement/embedded Runtime Lock finalization path still requires one freshly rebuilt-package
Docker retest.

That next Docker retest confirmed both preceding fixes far enough to pass the precise Docker wait
and the managed Benchmark reader. It persisted a complete 1.039-second software `stat` Collection
(`collection-318dd5292ec6c4ec`, 246 bytes, no fallback) and a bound partial resource context before
failing internal managed-session settlement with `Docker run exceeded its reserved resource
budget`. The failure was not a CPU, memory, or PID limit breach: settlement still measured from
tool entry through post-exit finalization and rounded that total against the three-second workload
lease. The candidate now records the workload-exit monotonic timestamp and settles only the
Gate-to-exit lifetime, capped by the already authorized integer reservation. Focused Docker tests
pass. The same report exposed that bounded paging omitted public Docker optimization and Container
Target artifact types; the candidate now admits those exact known-ID types without exposing private
build archives or enumeration. The complete Container Run/Benchmark/Measurement/embedded Runtime
Lock publication chain still requires one freshly rebuilt-package retest.

On 2026-09-18 that freshly rebuilt-package retest completed the whole single-confirmation Docker
path. One new Preview authorized one baseline Build and one managed `stat` collection with embedded
Native exact evidence; no standalone Runtime Lock authorization was created. Container Run
`container-run-2c7cc42af0e68ded81f2` exited zero and was removed, Collection
`collection-2be864f0ca9d793a` was complete software evidence without fallback, and Benchmark

not support a resource-transfer or performance-improvement claim.

The following release-blocking matrix entries are not inferred from nearby versions: JDK 17,
CPython 3.13 free-threaded, and Go 1.25/1.26/1.27 require their fixed, reviewed local runtime images
or native installations. PerfLens does not build or pull those images. Until they pass, v0.4.0
must remain an untagged release candidate and must not be described as fully stable.

## Required real-host closure

The bounded real-host script, the five locally available host Adapter paths, collection-summary
consistency, Finalization discoverability, and the single-authorization Docker integration have
passed. Before tagging, JDK 17, CPython 3.13 free-threaded, Go 1.25/1.26/1.27, and a stable Native
1% overhead result on a controlled host remain open.
Rootless Docker and explicitly enabled rootful targets remain separate environment assertions.

Package uninstall/non-activation and deployment rollback failure paths are already tested in
isolated package and transaction suites. A production host must not be destructively uninstalled
merely to repeat those tests; operators may perform that lifecycle only on a disposable host with
the old package artifacts available.

Only after the real-host output is reviewed, the remaining runtime matrix is either passed or
accurately limited, the final full gates are rerun, and the worktree is clean may the release
commit be created. Tagging and pushing remain separate explicit operations.
