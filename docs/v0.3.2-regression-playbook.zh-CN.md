# PerfLens v0.3.2 Docker 优化链路防回归手册

简体中文 | [English](v0.3.2-regression-playbook.md)

本文是 v0.3.2 发布后的维护合同，记录已经修复的故障为什么会发生，以及后续修改必须保持的
不变量。它不是当前缺陷清单；用户可见的历史症状和版本处理方式仍以
[《已知问题》](known-issues.zh-CN.md)为准，常规排错入口见
[《故障排查》](troubleshooting.zh-CN.md)。不得移动已经发布的 `v0.3.2` Tag 来纳入本文。

## 正确的托管采集时序

`stat` 和 `record` 的正常路径必须保持如下顺序：

```text
Preview 与一次明确授权
  → 构建并验证会话内 Build
  → 签发单次 workload lease
  → 创建容器，package Gate 阻塞 PID 1
  → 可选 PMU 可用性 probe（绝不发送 ready）
  → 启动最终选中的正式 profile，事件保持 disabled
  → perf 确认 disable 屏障
  → 重新核验 PID/UID/start time/namespace/cgroup
  → perf 确认 enable
  → 只发送一次 Broker ready，Gate 才 execve workload
  → 完成采集、发布 Artifact、核验并清理容器
```

availability probe、测试替身、fallback 分支或错误恢复路径都不能提前放行 Gate。这里的
ready 表示“最终正式 profile 已绑定到同一个已复核目标”，不是“Docker 可用”、
“perf_event_open 成功”或“授权已经存在”。

## 已修复问题与永久不变量

### 1. 不受支持的 perf `ping` 控制命令

- 历史现象：Gate 放行前返回 disabled-event binding handshake 错误；测试替身通过，真实
  Linux perf 失败。
- 原因：`perf stat/record --control` 的公开协议支持 `enable`、`disable`，并不保证支持
  `ping`。
- 不变量：事件以 `-D -1` 启动；使用幂等 `disable → ACK` 作为绑定屏障，重新验证目标后
  才发送独立的 `enable → ACK`。测试替身不得接受生产 perf 不支持的命令。

### 2. PMU probe 提前放行快速 workload

- 历史现象：较慢 baseline 成功，优化后的快速 candidate 在正式 profile 绑定前退出；换成
  `software_only` 偶尔看似恢复。
- 原因：availability probe 和正式 profile 共用了 Gate-ready 回调。
- 不变量：probe 的 ready 回调必须为空；只允许最终选中的正式 profile 放行一次。阻塞 Gate
  上的零 cycles/instructions 即使带有运行百分比，也不能证明 PMU 能为真实 workload 产生
  有用计数。`auto` 可保守降级；需要硬件证据必须显式选择 `hardware_required`。

### 3. 控制握手超时、管道反压和错误降级

- 历史现象：启动速度稍慢或 perf stderr 较多时偶发握手失败；`auto` 可能错误进入软件重采。
- 不变量：`disable → 身份复核 → enable` 共用一个有界、感知子进程存活状态的启动截止时间；
  Python Collector 等待 ACK 时持续排空有界诊断管道。超时、提前退出、通道关闭和非法 ACK
  都属于 `perf_control` 基础设施错误，不是 PMU 不可用，不能触发 fallback，也不能放行 Gate。
  不得用增加全局 pytest 超时或无限等待掩盖竞态。

### 4. lease 后失败的计费和重试边界

- 历史风险：失败没有形成 Collection 时，Agent 可能把它当成“未执行”，换 `stat/record`
  模式继续调用，或者在同一 Session 继续构建。
- 不变量：workload lease 签发后的失败精确计费一次，释放未使用的时间/证据预留，并永久阻止
  该 Session 后续 build/collection。不得原样重试、换证据模式或占用 build/test 可恢复重试
  预算。lease 前的拒绝不计费，但同样必须先修正原因。基础设施修好后重新 Preview 和授权。

### 5. candidate 已构建但没有 A/B Iteration

- 历史风险：采集或正确性在比较前失败，旧接口只能接收 Iteration，容易把 Build ID 错当成
  Iteration ID，或虚构 `not_comparable`。
- 不变量：使用 `not_evaluated` Disposition，绑定最新 `candidate_build_id` 和类型化
  `evaluation_reason`。恢复 baseline 不需要接受 token；保留未评估 candidate 必须再次得到
  新鲜明确同意。人工选择只记录最终 workspace，不会产生或升级性能结论。

### 6. 证据质量不能被 Benchmark 数字覆盖

- `actual_event_source`、固定环境、正确性、Benchmark、Profile 验证、资源转移和确定性重放
  必须共同满足，才能输出 `Verified Improvement`。
- `partial` Profile、内核 `[unknown]` 权重或 cgroup 下界不能被一个很大的 wall-time 改善
  覆盖。若用户态符号完整而受限内核帧未解析，应分别报告，不能把内核 unknown 归因到某个
  用户函数。
- 没有 Iteration 时必须写 `not_evaluated`；有 Iteration 但证据不完整时才可能是
  `not_comparable`。两者不能互换。

### 7. 容器身份、cgroup、Artifact 和符号边界

- `Docker target pid namespace identity is unavailable` 不是 Agent 确认弹窗被跳过。目标绑定
  必须由 Docker 返回值和 `/proc/<host-pid>` 的 PID namespace、start time、UID、cgroup
  身份共同证明；任一项缺失都要在采集前拒绝。
- 短命容器删除 cgroup 时，只能使用采集前固定的 `O_PATH` 锚点和最后一次身份已验证快照，
  并把资源差值标成 `partial` 下界。不能扩大 allowed root、跟随替换路径或把下界写成精确值。
- 语义 workload fingerprint 可以跨会话稳定，但每个带时间的 WorkloadSpec/Collection Artifact
  必须有内容绑定的唯一 ID。同 ID 不同内容是冲突或篡改信号，不能通过删除旧证据处理。
- 容器模块验证和用户态源码映射与受限内核符号是两个质量维度。内核 `[unknown]` 不得降低
  已验证用户模块的身份质量，也不得被错误归因到该模块。

## 禁止采用的“快速修复”

- 在 PMU probe、能力检查或容器创建完成时发送 ready；
- 把零硬件计数视为 PMU 可用，或把 `perf_control` 故障改写成软件 fallback；
- 在同一 optimization Session 自动重试失败采集或改用另一个模式；
- 通过放宽 PID、namespace、cgroup、路径或 Artifact 身份校验让流程继续；
- 删除冲突 Artifact、全局 prune Docker 对象，或绕过 Broker 直接运行 Docker/perf；
- 因 Benchmark 改善明显而跳过 Profile、资源或正确性门禁；
- 用人工“保留 candidate”伪造 `Verified Improvement`。

## 回归测试映射

修改 Collector、Helper、Gate、PMU fallback、optimization 状态机或 MCP finalizer 时，至少运行：

```bash
.venv/bin/pytest -q \
  tests/unit/test_collector_broker_security.py \
  tests/integration/test_collector_broker.py \
  tests/unit/test_docker_optimization_runtime.py \
  tests/mcp/test_server.py

cargo test --locked --package perflens-privileged-helper
```

关键测试合同包括：

- `test_cap_perfmon_auto_probe_keeps_managed_gate_blocked_until_formal_profile`；
- `test_cap_perfmon_does_not_misclassify_control_failure_as_pmu_fallback`；
- `test_cap_perfmon_does_not_retry_formal_control_failure_as_software`；
- `test_failed_workload_is_charged_and_blocks_unchanged_session_retries`；
- `test_runtime_finalizes_unevaluated_candidate_after_collection_failure`；
- Rust 的 `perf_binding_allows_a_slow_live_startup_within_the_bounded_window`、
  `auto_collection_does_not_hide_control_failure_with_software_fallback`、
  `formal_hardware_stat_requires_a_usable_requested_counter` 和
  `auto_collection_falls_back_to_fixed_software_events_within_the_duration`。

这些专项测试通过后仍要执行[发布流程](releasing.zh-CN.md)中的 Python 3.12/3.13、覆盖率、
Ruff、Pyright、Schema、Rust fmt/clippy/test/audit/deny、可复现包和 DEB smoke 门禁。

## 真实主机验收断言

安装匹配版本的主包和 Collector 包、重启三个服务并重新加载 Agent/MCP 后，使用一个新的
显式授权会话执行短时验收。不要复用失败 Session。报告至少核对：

- Gate 只在正式 profile 就绪后放行，workload 正常退出；
- 一次请求只增加一次 `workload_runs_used`；失败也只计费一次且禁止同会话继续；
- Collection 的 `actual_event_source`、`fallback_used`、`fallback_reason` 与请求一致；
- baseline/candidate 使用相同实际事件来源；
- 正确性和 Benchmark 绑定到各自 run，临时容器 `cleanup_status = removed`；
- `partial`、unknown、资源下界和禁止结论完整保留；
- candidate 已构建但在比较前停止时生成 `not_evaluated`，而不是伪造 Iteration。

若历史错误在匹配包和新会话上再次出现，应保存 Error ID、请求 ID、Session/Build/Collection
ID 和有界 journal，立即作为回归处理。不要连续重试，也不要修改 sysctl、systemd capability
或 Docker 安全边界来“验证”它。
