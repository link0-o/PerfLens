# PerfLens v0.4.0 发布候选就绪记录

简体中文 | [English](v0.4.0-release-readiness.md)

2026-09-18 状态：**最终本地发布门禁、真实主机安装/Collector 验收、当前本机可用的 Runtime
Lock 路径及一次确认的 Docker 集成已通过，固定版本矩阵与受控主机 Native 开销门禁仍待完成**。本文记录
八个 Runtime Lock 阶段提交之后、尚未打 Tag 的 `0.4.0` 候选版本。它不表示 GitHub
Release 已存在，不代替远端 CI，也不会移动不可变的 `v0.3.2` Tag。

## 候选范围

候选版本新增严格的 Runtime Lock Evidence Schema 1.1、有界会话、独立重放校验、Native
pthread、Java JFR、CPython threading 与 Go pprof Adapter。Docker optimization Preview
也可以显式把 Runtime Lock 权限纳入同一次用户确认。它不增加 JVM/native/Python live
注入、不向任意已有容器注入、不扩大特权 Helper capability，也不自动 commit、push、Tag
或发布。

## 真实主机安装与 Collector 证据

管理员已在 Debian 13 amd64 主机完成 `0.3.2-1` → `0.4.0-1` 升级验收。两个包均报告
`0.4.0-1`，CLI、MCP 与管理员 CLI 均报告 `0.4.0`。包安装没有改变三个已启用服务的激活
状态；经显式管理员升级后，非特权 Collector、受限 stat/record Helper 与独立 Trace Helper
均通过健康检查。部署策略内容和已有状态得到保留。

固定 Runtime Lock payload 均为 `root:root`、无 file capability；pthread probe 为 `0644`，
Runtime Lock supervisor 与 container Gate 为 `0755`。Native probe 同时通过 `GNU_RELRO` 与
`BIND_NOW` 检查。正式 Collector 策略为 root 所有、`0644`；项目生成、尚未部署的候选策略
仍保持调用用户所有、`0600`，两者不能混淆。

真实 1 秒 Host Collector 验收 `acceptance-f272e6a1a5605bd819fc` 状态为 `passed`：软件计数、
`cpu-clock` 采样以及 `sched`、`off_cpu`、`lock` 三类目标过滤 Trace 均成功。Trace Evidence
状态均为 `complete`，确定性分析/验证为 `partial` 并保留证据边界。主机硬件 PMU 不可用，
因此该验收不能支持 IPC、缓存未命中或分支未命中结论。

验收主机可发现 JDK 25.0.4.1、CPython 3.12.13/3.13.5 与 Go 1.24.4。通用 Host
Collector 验收项目没有为四类 Adapter 绑定安全目标和工具路径，因此 `status` 中主动 Adapter
显示 `unavailable` 是预期的项目配置状态，不代表 Adapter 实现缺失；其真实 Evidence 采集仍由
下述独立内容绑定会话验收。

第一次真实 Adapter 会话已完成 Native pthread exact 与 JDK 25 JFR thresholded 主路径。
Native Run `runtime-lock-run-279a6571fc25b673a2e8` 和 Java Run 的目标均以普通用户身份正常
退出，两个会话随后显式撤销。两条采集时生成并持久化的强验证记录均为 `verified`，包含路径
无关、内容绑定的 source replay receipt；对公开 Evidence 的再次离线验证会在没有私有原始流时
保守显示 `partial`，不得覆盖或贬低采集时的强验证记录。

Native Evidence 触及 20,000 条 exact 事件上限，状态因此为 `partial`。它证明了上限、配对、
等待/持有聚合和截断披露正常，但不能作为“未截断 exact”发布证据，必须以更低事件率重新验收。
JDK 25 balanced JFR 记录了超过 10 ms 阈值的 monitor 等待和调用栈；未记录事件仍不能解释为
没有等待，且 JFR 不提供完整 acquire/release 配对，因此禁止精确竞争次数、owner 关系和持锁
时长结论。

该轮和后续 Python 矩阵复测共暴露并在候选源码中修复了四个发布缺陷：Debian 常见的
`/usr/bin/python3` 发现符号链接
现在只作为位置提示，最终授权仍绑定解析后的非符号链接解释器；`perflens status` 现在执行与
MCP 一致的安全只读 Adapter 发现，会隔离单个不安全 Adapter 而保留其他状态行，并且不再把
缺少发现上下文误报为“尚未实现”。描述符执行现在还会绑定不可被组用户或其他用户写入的
Runtime Home 目录，并由
supervisor 内部传入固定描述符路径，使可重定位 CPython 3.12 无需接受任意环境变量即可找到
标准库。修复后的 DEB 已完成两轮逐字节一致的重建并通过隔离包冒烟。

持久化的 Verification 均包含非空 source replay receipt，且 10 项检查全部通过。所有 Evidence
loss/truncation 计数均为 0。Evidence `quality.status` 与 Run `quality_status` 是不同合同层：例如
Native Evidence 为 `complete`，而 Native Run 仍保守保持 `partial`。

`runtime-lock-run-finalization-f78296fe73a5e913a43b`、
`runtime-lock-run-finalization-90972afbd1a221f5d255`、
`runtime-lock-run-finalization-507a0445fe32c91ae2b5`、

2026-09-15 的下一轮安装包验收已完成 Native 与 JDK 21 宿主采集，随后在 CPython 停止：

exact binding，且 JFR 的零 DataLoss 字节不能直接读取。当前候选已支持显式 Adapter→语义映射，

后续一轮全新安装包验收成功执行了本机五个 Adapter：每个 workload 的正确性均通过，每条
采集时 Verification 都带 source replay receipt 且十项检查全部通过，Native/JFR Evidence 的
丢失与截断计数仍为零。Docker baseline 构建同样成功，Broker 还持久化了一条完整、无 fallback
的 1.041 秒软件 `stat` Collection；但三秒 workload 超时从容器准备前就开始，整数向上取整后
只给两秒 workload 留下约一秒 Docker wait，因此 Container Run、Benchmark、Measurement 与
Runtime Lock 尚未完成便失败。当前候选已改用保留小数精度的 Gate 放行相对截止时间，并把
真实等待超时明确归类到 Docker workload 阶段；仍需使用重建安装包复测 Docker。

该重建安装包复测已经确认 Gate 相对超时修复有效：同一个两秒 workload 的 Docker wait 不再
超时，Broker 持久化了完整的 1.027 秒软件 `stat` Collection；本机五条 Adapter 路径也再次
完成，source replay 均通过且 Evidence 未截断。随后 finalization 暴露了第二个独立缺陷：
Benchmark capture 要求 scratch 叶目录为 `0700`，而托管 coordinator、Docker mount 校验和
Runtime Lock capture 正确要求“私有 `0700` 运行目录下的 `0733` 容器可写叶目录”。当前候选
已改为校验这一真实两层布局，并把 Benchmark 文件 owner 独立绑定到已验证目标的宿主 UID；
Container Run、Benchmark、Measurement 与内嵌 Runtime Lock finalization 仍需再用一次全新
构建安装包完成 Docker 复测。

下一轮 Docker 复测已经执行到足以确认前两项修复：精确 Docker wait 和托管 Benchmark 读取器
均已通过；本轮还持久化了完整、无 fallback 的 1.039 秒软件 `stat` Collection
（`collection-318dd5292ec6c4ec`，246 bytes）及其绑定的 partial 资源上下文。随后内部托管

PID 上限超限，而是结算仍从工具入口一直计到 workload 退出后的收尾，再把总时间向上取整后
与三秒 workload lease 比较。当前候选已记录 workload 退出时的单调时钟，只结算 Gate 放行至
退出的生命周期，并限制在已授权的整数预留内；定向 Docker 测试已经通过。同一报告还暴露了
有界分页漏掉公开 Docker optimization 与 Container Target Artifact 类型；
当前候选已允许按精确已知 ID 读取这些类型，但不开放私有 build archive 或枚举能力。完整
Container Run、Benchmark、Measurement 与内嵌 Runtime Lock 发布链仍需再用一次全新安装包复测。

Lock 授权。Container Run `container-run-2c7cc42af0e68ded81f2` 以零退出并成功移除；Collection

端到端容器区间为 5.509 秒，而 Session 只结算三秒，证明准备及退出后收尾不再消耗三秒
workload lease。最终显式 revoke 保留了一次 workload、一次 Runtime Lock 运行及全部已结算身份；

## 必须完成的真实主机收口

有界真实主机脚本、当前本机可用的 5 条 Adapter 路径、采集摘要一致性、Finalization
可发现性回归及 Docker 一次授权集成已经通过。打 Tag 前尚需完成 JDK 17、CPython 3.13
