# PerfLens v0.3.1 一次性 Goal 执行合同

[English](v0.3.1-execution-contract.md)

本文不是产品能力路线图。Docker 的功能、安全和验收要求以
[`docker-container-roadmap.zh-CN.md`](docker-container-roadmap.zh-CN.md) 为准；本文只规定
Codex 如何持续实施该路线图，并在对话压缩、附件化或重新打开项目后可靠恢复进度。

## 1. 为什么需要独立执行合同

长期 Goal 不应把完整路线图、历史聊天和每次测试输出都复制进提示词。内容重复会增加
上下文冲突，旧状态也容易覆盖 Git 中的新状态。

v0.3.1 使用四层信息源，优先级固定为：

1. 当前 Git 工作区、提交历史和测试结果；
2. 仓库根目录的 `AGENTS.md`；
3. 中英文 Docker 路线图；
4. 本执行合同。

聊天记录、旧附件、界面中的文件计数和先前口头阶段报告都不是进度真相。它们与 Git
冲突时必须忽略。

## 2. Goal 开始和每次续跑的恢复协议

开始或续跑后，执行任何修改前必须运行：

```bash
git status --short
git log --oneline --decorate origin/main..HEAD
git diff --stat
git diff --check
```

然后按以下规则恢复：

- `v0.3.0` Tag 和 `origin/main` 是已发布基线，不移动、不覆盖；
- `origin/main..HEAD` 中通过测试的提交是已完成工作，不重复实现；
- 未提交文件属于当前阶段，先审查和验证，不盲目丢弃、提交或重写；
- 当前阶段由差异涉及的合同、Schema、实现和测试共同确定，不从聊天中的“Stage N”推断；
- 如果代码、路线图和旧状态说明冲突，以代码、测试及路线图为准，并在继续前说明冲突；
- 只有确有同一阻塞条件反复发生，才报告阻塞；测试失败本身不是停止 Goal 的理由。

不得依赖附件路径保存唯一需求。即使 Goal 正文被转成 pasted-text 附件，也必须能只靠
本仓库文件和 Git 恢复。

## 3. 固定实施循环

每轮只处理一个逻辑完整、可回滚的子功能：

1. 对照路线图确定当前第一个未完成能力；
2. 审查已有未提交实现，保留可证明正确的部分；
3. 完成正常路径、安全拒绝路径、资源边界、身份替换和篡改测试；
4. 运行本阶段对应的 Ruff、Pyright、pytest、Rust、协议和 Schema 检查；
5. 审查公开 Artifact、错误、日志和 Agent 可见投影是否泄露敏感信息；
6. 仅在本阶段检查全部通过后创建一个独立提交；
7. 报告提交哈希、测试结果、剩余边界和下一个阶段；
8. 自动继续，不等待用户重复输入“继续”。

每次提交后使用以下简短检查点格式：

```text
Checkpoint
- HEAD: <commit>
- 完成: <路线图能力>
- 验证: <命令和结果>
- 工作区: clean | <当前未提交阶段>
- 下一步: <唯一下一阶段>
- 需要用户操作: none | <原因>
```

检查点是摘要，不复制长日志。详细证明保留在测试、Artifact 和 Git 提交中。

## 4. v0.3.1 固定实施顺序

顺序以 Docker 路线图第 10 节为准：

1. Docker 公共 Artifact、Schema 和能力发现；
2. 固定 Docker Adapter、Socket 身份固定和有界脱敏解析；
3. 容器 ID、Host PID、UID、start time、namespace、cgroup 和 PID 复用验证；
4. cgroup v2 资源快照、差值、质量模型和 verifier；
5. 已有容器的单 PID plan → policy → broker → artifact 路径；
6. Container Gate、临时测试容器启动和失败清理；
7. `per_run`、对话级 `bounded_session`、撤销、过期和预算；
8. rootless、同 UID 和显式授权 rootful 边界，以及 Broker/Helper 独立复核；
9. 容器模块、Build ID、源码映射、软件 PMU 降级和诊断绑定；
10. CLI、`perflens init --docker`、MCP、Skill、Codex/Claude 配置和匹配 A/B；
11. 两个 DEB、升级/回滚/卸载、宿主机回归、双语文档和真实 Docker 矩阵。

大阶段可以拆成多个小提交，但不得跳过身份、授权或拒绝路径去提前开放 Docker 执行。

## 5. 自主范围和暂停条件

Goal 可自行读取文件、编辑仓库内代码、运行非破坏性检查、构建本地包和创建本地提交。
以下行为不属于一次性授权：

- `sudo`、sysctl、systemd、`/etc` 或已部署 Collector 修改；
- push、创建/移动 Tag、Release 发布；
- reset、amend、删除提交或修改现有 stash；
- 安装 Docker、修改 Docker 用户组或启用 rootful 策略；
- 实现 v0.4.0 Runtime Lock Adapter；
- 为通过 CI 降低覆盖率、删除测试、放宽安全检查或提高全局超时。

需要 root、真实 Docker 或主机服务验收时，应先完成所有可在普通用户环境完成的工作，
把命令合并为一个可审查批次，然后暂停等待用户执行。收到完整输出后从 Git 检查点继续。
因此“一次性 Goal”表示无需反复输入“继续”，不表示可以绕过必要的管理员授权。

用户说“暂停”“停止”或“先别改”时立即停止。

## 6. 完成条件

只有以下条件全部满足才能结束 Goal：

- 路线图中的稳定 Docker 功能全部实现；
- 每个子功能有独立提交和通过的正常/拒绝/边界测试；
- Ruff、Pyright、Python 全量测试、Rust、协议和 Schema 检查全部通过；
- 测试覆盖率不低于 85%；
- `stat`、`record`、`sched`、`off_cpu`、`lock` 的容器目标路径符合功能配置边界；
- 软件 PMU 降级、符号/源码绑定和匹配 A/B 不夸大证据；
- 两个 v0.3.1 DEB 构建并通过安装、升级、回滚、卸载和不自动启用 Docker 的 smoke；
- v0.3.0 Linux 宿主机路径无回归；
- 中英文文档与实现一致；
- 必需的真实 Docker/主机矩阵已经由用户执行并通过；
- 工作区干净；
- 最终报告列出提交、测试证据、已知边界和本地安装验收命令。

缺少真实主机结果时 Goal 只能暂停等待，不能宣称完成。

## 7. 推荐的 `/goal` 提示词

在项目根目录打开 Codex，使用下面这段短提示词。不要再附加整份路线图或旧聊天记录：

```text
/goal 完整实现 PerfLens v0.3.1 本地 Docker 单进程性能采集与分析，并持续工作到 docs/v0.3.1-execution-contract.zh-CN.md 定义的全部完成条件通过。

开始前及每次续跑必须完整读取：
- AGENTS.md
- docs/docker-container-roadmap.zh-CN.md
- docs/docker-container-roadmap.md
- docs/v0.3.1-execution-contract.zh-CN.md

唯一进度真相是当前 Git 状态、提交历史和测试结果；忽略与 Git 冲突的旧聊天、附件、阶段编号或口头报告。从 Git 证明的第一个未完成阶段继续，保留并审查已有未提交实现，不重复已提交工作。

严格执行执行合同中的单阶段循环：完成实现、正常/拒绝/边界测试、静态检查、安全审查，通过后独立 commit，报告短检查点并自动继续。范围只限 v0.3.1 Docker，不实现 v0.4.0。

不使用子 Agent，不运行 sudo，不修改 sysctl、systemd、/etc 或已部署服务，不 push、不创建或移动 Tag、不发布 Release、不 reset/amend、不修改现有 stash。需要 root 或真实 Docker 验收时，在所有普通用户工作完成后汇总为一次命令并暂停等待我的输出。
```

如果已有 Goal 正在正确执行，不要为了换提示词清空它；先用 `/goal` 查看状态。只有 Goal
目标已经被旧内容污染或与本合同冲突时，才先 `/goal pause`，确认 Git 工作区，再清理并用
上面的短提示词创建新 Goal。暂停或更换 Goal 不会替代 Git 检查点。

## 8. 推荐运行设置

- 模型：适合长周期代码任务的 Codex 模型；
- 推理程度：默认 `xhigh`；
- `max`：仅用于最终安全审查、难以定位的跨语言协议问题或发布前总验收；
- 不默认使用多 Agent，因为 Docker 身份、Python Broker 和两个 Rust Helper 修改共享协议，
  并行写入更容易造成阶段交叉。

推理程度不能修复上下文冲突；精简 Goal、稳定仓库文档和可验证 Git 检查点才是主要机制。
